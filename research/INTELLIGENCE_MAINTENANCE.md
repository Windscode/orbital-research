# 研究情报与来源库维护

每次扩展情报时，先读取 `intelligence-sources-v9.json` 和 `intelligence-maintenance-v9.json`。来源库是持续维护的研究入口，不是一次整理后固定不变的白名单；仍需做主题、地区、语言和方法的补充搜索。

## 准备与搜集

1. 明确本轮主题、日期范围和覆盖缺口。网站「搜集与维护」可导出资料包；也可在仓库根目录运行 `npm run research:packet -- --topic "月面热控"`。可选参数见 `--help`。
2. 从相关机构、企业、论文、软件/数据与专业媒体入口查阅。先读来源的 `whatToLookFor`、`checks`、`accessNote` 与 `verification`，不要把访问受限或仅索引核对的记录当作全文核实。
3. 使用维护数据中的检索模板做通用搜索与跨语言检索，补充来源库尚未覆盖的机构或主题。报道和企业稿提供线索；涉及方法、性能和状态的结论应继续寻找原始资料。
4. 打开具体文章、论文、任务文件或发布说明，记录原始 URL、DOI、版本、发布日期、事件日期、检索日期、主要证据、适用范围与未确定项。遇到访问失败就保留失败原因，不伪造查阅结果。

## 写入与复核

- 情报存入 `briefings.json`，沿用稳定 ID。按规范化 URL、DOI、同一事件及版本去重。更正旧事件时优先修订已有条目并说明修订理由，避免同一事实被包装成多条新进展。
- `publishedOn` 是原文发布日期；`eventDate` 仅在来源明确给出单日事件时填写，否则为 `null` 并解释时间区间或计划状态；`verifiedOn` 是本轮实际核查日期。研究推论在 `analysis` / `implication` 中说明是本站方法建议。
- 新来源需检查主体、原始发布能力、稳定入口、日期/版本信息、研究用途及访问条件。补齐来源数据全部字段，不仅保存一个链接。保留 `page-read`、`search-result`、`access-limited` 三类核查方式的差异。
- 已停止更新的来源改为 `archive`；迁移、失效或状态不清的来源改为 `review` 并记录原因。不要将一次抓取失败直接解释成网站永久关闭。保留历史引用，避免删除仍被旧条目引用的入口。
- 来源状态或入口发生变化时，在 `intelligence-maintenance-v9.json` 的 `history` 中记录日期、修改与原因。版本文件名可保持不变；破坏 schema 的改动才需要同步迁移代码和测试。
- 运行 `npm run check:intelligence`、`npm test`、`npm run build` 和 `npm run check:bundle`；在浏览器查看日期、筛选、来源关联及详情。数据检查验证结构和关联，不能代替联网事实核查。

## 网站中的本地状态

关注清单只存储来源 ID，保存在当前浏览器 `orbital-intelligence-watch-v1`；它不修改共享库。网页导出的来源提案处于 `unreviewed` 状态，需人工审查后写入仓库。网页与 CLI 资料包都不抓取网页、不自动发布情报，也没有设置定时任务。

初始整理为 47 个来源：32 个入口已阅读、5 个通过索引核对、10 个访问受限。该统计仅描述 2026-10-26 的核查记录，后续更新时应重新统计，而非沿用为当前状态。
